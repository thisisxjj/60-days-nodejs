1. 先建立四个基础事实

① 线程是一条执行流。 一个线程一次只能做一件事,代码一行一行往下执行。
② 程序不能直接读硬盘或网卡。 要读文件或网络数据,程序必须请求操作系统内核帮忙,这个请求叫系统调用,比如 read(fd, buf)。fd(文件描述符)是一个整数,用来代表一个已打开的文件或网络连接。
③ I/O 比 CPU 慢很多。 读内存约 100 纳秒,读 SSD 约几十到几百微秒,读机械硬盘约几毫秒,一次网络往返几毫秒到几百毫秒。差距是几个数量级。
④ read 默认是阻塞的。 调用时如果数据还没准备好,内核会把这个线程挂起:线程不占 CPU,但在数据到达前什么也做不了,调用也不会返回。

2. 服务器面临的问题

服务器要同时服务很多客户端。传统做法是每个连接一个线程:

```javascript
// 伪代码:每个线程里的代码是顺序执行的
data = read(连接)      // 数据没到,这个线程被挂起
result = 处理(data)
write(连接, result)
```

这种写法直观。问题是有 1 万个连接就需要 1 万个线程,每个线程占独立的栈内存,内核在线程之间切换也有开销。
Node.js 选了另一条路:只用一个线程执行所有 JavaScript 代码。这就带来一个硬性要求:这个线程永远不能被挂起。一旦它在某个 read 里挂起,所有连接都得等。

3. 线程不能挂起,数据怎么读?

> 办法一:非阻塞 read + 就绪通知(用于网络)

内核允许把 socket 设为非阻塞:调用 read 时没有数据,不挂起线程,立刻返回错误码 EAGAIN,意思是「现在没有,稍后再试」。
但不能每隔一会儿就问一遍,那会白白占用 CPU。所以内核还提供了 epoll(Linux)这类机制,用法是:
1. 把 1 万个 socket 的 fd 一次性登记给内核(epoll_ctl)。
2. 调用 epoll_wait:线程在这里睡眠,不占 CPU。
3. 只要其中任意一个 socket 收到了数据,内核就唤醒线程,并告诉它「fd=12 可读了」。
4. 线程对 fd=12 调用 read。数据已经在内核里,read 瞬间完成。
5. 回到第 2 步继续睡。

这样一个线程就能同时盯着上万个连接,并且只在有活可干的时候醒来。这种「一次登记很多 fd,哪个就绪通知哪个」的做法叫 I/O 多路复用。
epoll 是 Linux 的实现,macOS 是 kqueue,Windows 是 IOCP(它的通知方式略有不同,这里不展开)。

> 办法二:让别的线程替你等(用于文件)

办法一对普通文件行不通。Linux 上,普通文件不支持非阻塞模式,也不能登记进 epoll,read 一定会等到读完才返回。
这时只剩一个办法:另开几个线程,专门执行这些会挂起的调用。主线程把「读这个文件」的任务交给它们,自己继续干别的。
工作线程挂起没关系,反正它们存在的目的就是替主线程挂起。读完后,工作线程再通知主线程。
